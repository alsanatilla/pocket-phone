# pip — Pocket's assistant

Pip uses the API provider and model selected in settings. It has its own name across providers. Provider names remain visible in API and data-access settings so the destination of a request is clear.

## Daily brief

Apps and an optional Today tile open Pip’s brief of saved Pocket facts. Home and Today lead with actual COROS stat bars. The brief is generated locally, with matching Java/browser rules, and reads no provider or network service. Recovery uses actual saved sample dates; calendar uses local day boundaries; task priority respects your chosen next action. Only thoughts with an explicit revisit time appear as ready. Gym distinguishes finished sessions from a workout in progress.

Each fact opens its source. **Think with Pip / ask Pip** starts a fresh unsent draft containing at most 6,000 characters of brief context, preserving other drafts. Send uses that chat’s configured provider and existing tool permissions. Reading the brief needs no key; disabling it is a synced account preference. Existing source records remain the authority, so no generated brief is uploaded or treated as a new task.

## Repetition and caching

The concrete repetition bug was conversation history: Pocket joined a model's remarks before a lookup to its final answer and replayed that combined text on subsequent messages. Failed or stopped partial replies could also be replayed as ordinary answers.

Pip stores the answer separately from the provider's reasoning summary, lookup steps and pre-lookup remarks. Completed answers and their paired questions go into later requests. The browser also retains stopped, failed and interrupted questions with fixed no-answer markers; their partial answers and reasoning stay out of ordinary replay. The phone keeps its released completed-pair behavior. Retry replaces the partial answer; stopping invalidates late callbacks. Within one reply, the original tool-call text, IDs and signed thinking blocks are still retained for the provider's continuation protocol.

Prompt caching stays available on the phone. It reuses input prefixes; it does not replay generated answers. The persona and date are stable for an entire request, including its lookup rounds. Changes to model, access, thinking settings or the date can cause a cache miss. Short chats may not reach a model's minimum cacheable input length. Settings → storage & usage shows the reported read/write counts.

References: [Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [thinking summaries and supported configurations](https://platform.claude.com/docs/en/build-with-claude/thinking).

## Conversation storage

Chats, turns, drafts, reasoning and reported usage are in a private SQLite database under Android's no-backup directory. A transaction saves a chat and its turns together. The paid request waits for that particular chat's user message to be saved; a successful save in another chat cannot approve a failed write. Queued writes remain readable while switching chats. The provider's configured model is stored separately from a canonical model name returned by the API, so reloading a chat never drops its provider identity.

The prior single-chat JSON file is imported with its original validation. Its source is removed only after the database copy can be read. A damaged source is kept for recovery. Interrupted replies reopen as retryable failures and are never automatically sent again. There is no automatic deletion of older conversations. New chat keeps the previous conversation and its draft. Chats can be opened, renamed or explicitly deleted from the picker. One reply can run at a time; switching chats leaves it in its original conversation and offers an **open** command.

SQLite replaces the single whole-conversation file because it supports separate chats, atomic updates and an indexed conversation list without rewriting every saved conversation. Signed-in chats, drafts, context and reply activity sync through the Pocket account API between phone and browser. Account chats return on the next sync after clearing a local copy; guest chats are lost when their local data is cleared. Chats are excluded from legacy Drive sync and Android backups. API keys continue to use Android Keystore encryption and are not stored in the chat database.

## Activity, search and reasoning

The page uses Pocket's standard header, pixel title and headings, monospace body, accent emphasis, prompt lines and bottom send/stop control. Replies receive Markdown formatting during streaming; parsing is throttled for longer replies. Actual searches and local reads have their own activity section above the answer. It opens while a reply streams and folds to a compact summary afterward. Each step records its tool name, query/parameters, pending/running/completed/failed/stopped state, elapsed time, result summary and safe source links. Parameters stay behind an additional control. Activity is stored with the reply: private SQLite on phone and account-scoped browser records. Stop and interrupted native replies settle unfinished activity, and retries start a fresh activity list.

Reasoning stays separate. It shows only the provider's summary and remarks before a lookup; it is never presented as proof of tool execution. Legacy phone lookup lines remain readable in older replies. Signed thinking and encrypted search payloads exist only in the current request's continuation; they are not saved in the activity display.

Browser Pip uses Vercel AI SDK 7's `ToolLoopAgent` for provider streaming, tool-call parsing, tool definitions and input validation (zod schemas), tool execution, the user's approval of writes (`toolApproval`) and multi-step continuation. Anthropic, OpenAI, OpenRouter and other compatible endpoints use their SDK adapters, loaded when that provider is needed. Some open models (Qwen3-Coder, Nemotron and Hermes-style templates) write a tool call as `<tool_call>…` text when their host does not parse it; SDK language-model middleware turns such blocks into tool calls, so they are validated, run or refused like any other call instead of becoming the answer. Pocket supplies history, implements each granted tool, records actual outcomes, refuses repeated saves and reserves the final-answer budget through `prepareStep`. API keys stay in the current browser tab. Execution remains owned by the browser; closing it interrupts the reply, which can later be explicitly continued from recorded observations. See [the architecture decision](PIP-ARCHITECTURE.md) and [AI SDK agent configuration](https://github.com/vercel/ai/blob/main/content/docs/03-agents/02-building-agents.mdx).

The composer exposes **tools** and **web**. Pocket access starts off and is granted per API provider/endpoint. Notes, undecided Thoughts, chosen Tasks, Calendar, Gym and cached COROS readings each have their own read permission. `search_pocket` searches across permitted Notes/Tasks/Thoughts/Calendar. `read_task` includes due date, completion, steps and source context; note source text stays withheld when Notes access is off. `read_note` supports `offset`, `length` and `next_offset`. COROS reads use only its existing cache and never read its authentication store. Tools can read, display plans and save new records or change existing ones. On the phone they prepare proposals that only the user saves or applies; in the browser every save or change waits for the user to approve, edit or decline it.

Web search starts off. When enabled, Pip calls Firecrawl through `search_web` and `read_web_page` for every provider; the activity rows show the query labels and result links. Search errors are parsed even when the HTTP request succeeds. These work without a key at low volume; an optional Firecrawl key is stored like a provider key (encrypted on the phone, tab session in the browser). Page text is capped at 6,000 characters. On OpenRouter, a `:free` model or `openrouter/free` is sent with a `models` fallback list (Nemotron 3 Super, Ling 3.0 Flash, the free router), and HTTP 429/502/503 is retried twice before any reply starts. Unsupported provider/model settings fail visibly.

Both transports bound research to eight tool continuations, 20 client calls, eight web calls (including page reads), 48,000 characters of research data, 8,000 characters per result and tool input, 90 seconds without new stream activity and five minutes total; the phone also runs at most three independent reads at once. The configured reply token budget covers every round. Unfinished tool arguments never execute; results retain their original tool-call IDs even when independent reads finish out of order. On the phone, preparations wait for preceding reads and preparations; in the browser a write runs only after the user's decision, after the reads of its round. Inputs are validated before reads (in the browser by the AI SDK against each tool's schema), access is checked again, and results are untrusted reference data.

On the browser, finalization allows at most four plan/save calls across two extra rounds, then an answer, within the original token and time budgets. A final-round save reserves tokens for the answer even when usage is absent. App limits are supplied as system instructions, never fabricated user messages, and refer to the current request. A source/context/continuation limit without a final answer stays incomplete and resumable. Repeating an identical failed call returns its recorded failure and ends research instead of retrying the source; invalid arguments return the schema error to the model and never run. A save identical to one already approved, including before Continue or Restart, is refused without asking again. The phone retains its released final-synthesis behavior.

Browser web results retain news snippets, source types and reported dates; mixed searches interleave web/news hits rather than dropping all news behind a full web group. Page reads retain publication/modification metadata when supplied. HTTP-200 API failures, unsuccessful source-page statuses and empty page text are errors. The prompt includes the browser's local date/timezone and requires publication dates, data periods, partial excerpts and conflicting claims to be assessed explicitly. See [Firecrawl search response fields](https://docs.firecrawl.dev/features/search) and [scrape response status](https://docs.firecrawl.dev/features/scrape).

## Plans, approval and interrupted research

In the browser, writes are AI SDK tools gated by `toolApproval`: `create_record` (a new Note, Task or Appointment), `change_record` and `coros_write` (the changes described below). Before asking, Pocket checks the record as it is now and refuses without asking when the change cannot apply or was already saved. The reply then pauses with a card for each waiting write: **review** opens the same editable review as a proposal, and saving it approves the call with the edits; **decline** refuses it. The SDK validates the approved input again, runs the tool, and Pip continues with the outcome. Waiting counts against neither the idle limit nor the research deadline. Stop, or closing the tab, interrupts the reply and writes nothing. Proposals from earlier replies keep their review cards.

`update_plan` displays one to six pending/in-progress/done steps. `propose_action` prepares a Note, Task or Appointment without writing Pocket content; the browser's `create_record` saves one after approval. Plans, proposals and saves are available with Pocket read access off. The user reviews and edits a proposal, then saves it. Notes preserve title/text; Tasks preserve title, context, due date and up to 12 one-line steps of 160 characters; Calendar stores title, date/time and duration (15–480 minutes). Other proposal context stays in chat. Nothing promotes a Thought automatically.

Proposal and save IDs derive from the conversation, paired user turn and actual activity event. Repeated saves on another device reuse the record and preserve later edits. Deleted proposal records cannot be resurrected. Saved activity markers open the real Note, Task or Calendar record. These records and markers use existing account sync.

`propose_change` (the browser's `change_record`, applied after approval) prepares a change to an existing record: complete a task, update a task (title, due date or cleared date, up to six new steps), add text to the end of a note, or move an appointment (date/time and 15–480 minutes). It is offered when Tasks, Notes or Calendar access is on, and each change needs its own category. The tool checks the record as it is now. A missing, already completed or full record returns a visible error. Steps the task already has are dropped, and nothing is written until the user applies or approves it. The review shows the current state next to the editable change, with Pip's reason if given. Applying is idempotent. A completed task stays completed and is logged once. Steps and note text are added once. A moved appointment keeps its reminder at the same distance. Applied markers open the changed record and sync like saved proposals. Change proposals are never cached or replayed on Continue.

Live COROS (browser, 0.20 preview; phone to follow): with COROS access and a signed-in Pocket account, `coros_read` calls COROS's MCP tools live through the account, which holds the COROS connection: activities and laps, health, sleep, recovery, load, fitness, the training schedule, the workout library and training plans. Long answers page from the run cache. `coros_format` returns COROS's own rules and arguments for one tool in pages that fit the result limit. `propose_coros` (the browser's `coros_write`, sent after approval) prepares a workout change: a new workout on a date, a library workout on a date, a new library workout, or an edit to a scheduled or library workout. It checks dates (today to 90 days ahead), sports and sections, and for edits reads the current workout. Nothing reaches COROS until the user applies or approves it in the review, which shows the date, name, description and each section in plain words. The server applies each proposal once per proposal key, also across devices and double taps; a refused change shows COROS's reason and can be applied again. Pip waits up to 15 seconds for a running Movement refresh. Training plans stay read-only: a plan is larger than Pip's whole reply budget. COROS cannot remove workouts through Pocket; that happens in the COROS app.

Completed observations save with actual activity, bounded to 64 steps and 120,000 characters per reply. Browser retention prioritizes up to 32 user-applied action markers ahead of ordinary reads. **Continue** explicitly resumes the latest failed/stopped turn using completed reads that still match the provider and granted sources; the browser also accepts a restored streaming turn whose original request was interrupted. Plans/proposals remain visible, and saved actions are not proposed again. Idle/absolute deadlines and a final answer that exhausts its output budget stay incomplete and resumable; useful partial text remains visible and never enters ordinary completed-answer history. On the browser, **Restart** starts fresh research and answer text while preserving the earlier activity and saved-action journal. Neither runs automatically. Equivalent lookups share the run cache and say when cached. Restored composite reads and cache hits recheck live grants, including Tasks' note context and history's web access. An account change aborts late browser callbacks before they can write a reply into the new workspace.

Web searches accept up to five `domains`, `time_range` (any/day/week/month/year), `sources` (web/news/images) and `categories` (research/pdf/github), using Firecrawl's documented `includeDomains`, `tbs`, `sources` and `categories`. Pages support `offset`, `length`, `next_offset` and a query-focused passage, with a six-page cache per run. The model must still cite and assess returned sources. Firecrawl is Pip's web search for every provider.

Protocol references: [Anthropic tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works), [OpenRouter tool calling](https://openrouter.ai/docs/guides/features/tool-calling), [Firecrawl search](https://docs.firecrawl.dev/features/search).

The loader is the same pixel character on phone and web. It randomly waves, walks, juggles, reads, hops and plays a tiny gamepad, switching activities between short animation cycles. Both implementations draw the same 32-pixel geometry. It stops callbacks when hidden, paused or detached, and remains still with reduced motion or disabled Android animations. Geometric signal marks and short loading labels give the chat an early-console feel without adding explanatory copy, sound or a background animation loop.

The chat has the same static pixel glow on phone and web: only the upper-corner bloom, fading to black before the middle of the page. Sparks stay inside the light, and the conversation and composer sit on black. The artwork is cached by size on Android and painted only on resize in the browser; changing chats disconnects the old canvas observer.

## Browser and shared workflow

The component hierarchy follows [BeautifulUI](https://www.beautifului.dev/): conversation navigation, messages, compact tool activity, expandable reasoning, context cards and composer. The implementation and visual styling belong to Pocket: pixel headings, monospace text, accent color and compact controls. No framework or copied component library is required. The activity and source patterns were reviewed against [Vercel's tool component](https://elements.ai-sdk.dev/components/tool), [source disclosure](https://elements.ai-sdk.dev/components/sources) and [progressive disclosure guidance](https://www.nngroup.com/articles/progressive-disclosure/). The implementation follows Anthropic's [tool protocol](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls) and [web search events/citations](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool).

Phone and browser drafts can explicitly attach up to three Thought, Task or Note snapshots. Sources accompany the saved user message and completed conversation history. A source changing later does not silently rewrite a question. A reply or selected passage can be kept as a Note, parked as a Thought, turned into an editable Task or copied. These kept records enter Pocket's existing shared collections; a Thought does not become a Task automatically.

Conversations and drafts save locally first, then sync to the signed-in account on phone and browser; each reply merges by its own edit time, so two devices can continue the same chat. Guest chats can be copied into the account when signing in; provider keys are not copied. Keys use tab session storage; Anthropic's key is shared with Paper in the same tab, and compatible API keys are bound to their endpoints. Requests go directly to the chosen provider. Compatible endpoints must allow browser requests through CORS and support function tools when Pocket access is enabled. Explicit retry replaces one unfinished reply; changing provider starts a separate conversation. Clearing browser data removes guest chats; account chats are restored on the next sync. Its read-only tools read the browser's saved/synced Pocket records; they cannot reach device-only records.

Browser replay selects at most 20 prior turns within the existing 60,000-character selection budget, accounting for the current request, activity memory and coverage notice. It retains the first request and a contiguous recent window, including a bounded excerpt of an oversized newest exchange. Clipped requests and answers carry their turn ID and exact recovery offset. Unanswered questions keep their original order with a fixed status marker. A bounded coverage block reports selected, omitted and clipped turns and explains how to recover them. Completed proposal summaries retain their actual save status. This is a character-based selection budget, not a model context-window guarantee: system/tool definitions, serialized UTF-8 expansion, Continue checkpoints and later tool-round content still need a single model-aware total budget.

Browser conversation memory is projected from recorded activity, not generated recollection. Each request receives at most 12,000 characters of historical outcomes and source excerpts, including actions older than the ordinary replay window, and explicit omission counts. `read_chat_history` searches/pages earlier requests, final answers, tool outcomes and saved actions in this conversation only. Listings contain bounded excerpts, while queries match full requests, explicitly attached snapshots and completed answers. Match offsets locate hits outside an excerpt. A `turn_id` with `answer_offset` or `request_offset` reads exact text in bounded JSON pages using the corresponding next offset. Pages handle escaped text and surrogate pairs without empty continuation loops. An `event_id` retrieves a permitted recorded result as serialized JSON pages using `result_offset`/`next_result_offset`, without refetching its source. Tool result payloads are withheld when the recipient or grants no longer match, including composite history when web access changes. Provider reasoning and stopped or failed partial answers are excluded from listings, search and answer pages. Historical observations are dated reference data; current claims still need fresh evidence.

When a provider refuses a request as too long for its context window (for example `prompt is too long`, `context_length_exceeded` or HTTP 413), Pip shows a fixed context-limit message without exposing the provider's text or retrying. Output-limit configuration errors and validation echoes are not classified as chat overflow. Reading an error body respects cancellation and the inactivity deadline. The reply offers **new chat**, preserving the question and attached snapshots as an unsent draft, or **model settings**.

The browser composer's **history** control shows how many earlier turns the next reply includes. Its local search covers all stored questions and completed answers, labels included/excerpt/older turns and opens the original turn with keyboard focus. It sends no provider request. Draft changes refresh the coverage estimate. Each reply saves the replay selection actually used; available provider usage displays the last request's input/output tokens separately from aggregate multi-round usage. Anthropic input includes its uncached, cache-read and cache-creation buckets; compatible prompt-token counts already include cached tokens. Inactive unfinished replies are labelled partial/incomplete, pending tools are marked interrupted, and Continue/Restart explain their different behavior.

Further T3-inspired UI work needs matching runtime support: an editable message queue and steering controls; background-run status and completion notifications backed by jobs that survive a closed browser; edit-and-resend/fork controls; and a context-window meter plus compaction/history management. Model-aware budgeting and cached/compacted history come before a capacity percentage. The browser still runs replies locally and stops them on page exit.

The reply's **save note**, **park thought** and **make task** buttons record a user-kept action with the actual record link. Proposal approval records the edited payload and user-applied status; in the browser an approved save records its edited input and the saved record, and a declined one is remembered as declined. Later replies see these as a `[Pip actions: …]` line. Prepared, declined, failed and user-applied outcomes remain distinct. This is bounded memory of the saved conversation; it cannot recover events that were never stored or have been removed.

## Markdown on the web

Pip answers, reasoning summaries and note previews use the native Satteri 0.10.5 engine included with Astro 7.3.6. Nested lists, tables, task lists, reference links, footnotes, code blocks and headings render in the Warm Console layout. Thoughts and handwriting crops keep their existing note handles; code blocks remain literal. Rendering never changes a note or creates a task.

The browser posts text to Pocket's `/api/markdown` renderer, which neither stores nor logs it. The native compiler produces a tree; only allowed text, tags and links become HTML. Raw HTML stays visible as text, images become links, and footnotes scroll inside their own reply without changing the workspace route. Input, body, tree depth and output limits bound each request.

Streaming text appears immediately. Formatting is throttled and stale responses cannot replace a newer draft or paint another account's workspace. Up to 20 completed previews fit in a 600,000-character cache in that account's browser storage, separate from sync. Cached previews work offline; new or evicted text stays readable as plain text until the renderer is reachable. This pass updates the web only; Android remains at its released build.

## Search and account access

Pocket's global search finds saved Pip questions and answers on phone and web, including messages beyond the API's replay budget. Selecting a hit opens that conversation. Search uses the signed-in account's index and saved local records; it does not make a paid provider request.

Use the same Pocket account across devices. Passkeys are additional sign-in keys for that account; a phone can link through a short code approved in a signed-in browser. Creating an account and signing in are separate actions. Provider keys still stay on their device, so continuing a chat elsewhere requires configuring that device's provider key.

Coverage includes current-request priority, final synthesis budgets, schema errors, repeated failures/proposals, dated news results, durable activity memory, permission/account changes, reload recovery, saved-action sync, replay selection, clipped-request/answer recovery, escaped paging, long-chat continuation offsets, context errors and per-request usage. Browser checks cover edited note approval followed by a different question, ordinary reply saves, history search beyond excerpts, excluded partial-answer search, turn focus/navigation, desktop/mobile layouts, Continue recovery and context-overflow recovery into an unsent draft through either recovery action. The context UI pass used local headless Edge after the shared preview became unavailable. Provider/Firecrawl responses are simulated; no paid requests were made.

The 0.18 passes use focused native and browser fixtures; 0.18.1 also ran the full Android unit suite (555 cases; six failures predate 0.17). 0.19.0 adds change-proposal checks on both platforms: access gating, validation against live records, nothing written before apply, idempotent apply, reminder shift and the native review dialog. Native checks cover budgets, ordered parallel reads, cancellation, provider continuation state, permission-aware checkpoints, paged tools, portable approval IDs, persistence, deletion and actual review/save UI. SDK streaming fixtures cover Android API 24 and 35, including truncated model rounds and malformed tool arguments. Browser checks exercise multi-round streamed research, editable proposals, Continue/Restart, responsive layouts and two-way sync via a fictional account on a throwaway local database. Model and Firecrawl responses are simulated; no paid requests were made.

Physical passkey prompts, native sign-in and handset animations remain unverified. Actual build results and signing status are recorded in [BUILD-STATUS.json](BUILD-STATUS.json); another release agent handles APK signing.
